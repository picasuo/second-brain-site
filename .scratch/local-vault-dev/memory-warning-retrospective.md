客户端上线几周后，陆续收到用户反馈：应用挂在后台一整天，内存占用会从启动时的 200MB 左右，一路涨到 2GB 以上，最终触发系统的内存告警。

## 背景

问题只在长时间运行后出现，本地开发环境很难稳定复现，只能先通过日志和用户提供的截图定位大致方向。

最初的假设集中在自动更新、崩溃上报和渲染进程缓存三个模块，但这些路径在短时间压测里都没有明显异常。

## 复现步骤

1. 关闭自动更新和崩溃上报，排除干扰变量。
2. 打开应用后保持后台运行，每 30 分钟记录一次内存占用。
3. 在渲染进程里模拟高频窗口切换和 IPC 通信。
4. 约 4 小时后，主进程内存出现持续上涨且不回落。

## 排查过程

确认可以复现之后，用 Chrome DevTools 的 Memory 面板对主进程做了几次堆快照对比，重点看两次快照之间新增且没有被回收的对象。

### 内存快照对比

泄漏对象集中在窗口状态监听器附近，数量随着窗口切换次数线性增长。每次切换都会注册新的监听器，但旧监听器没有解绑。

### 定位可疑模块

进一步检查发现，模块在重新挂载时会重复订阅 IPC channel。组件销毁时只清理了局部状态，没有清理主进程侧的订阅句柄。

## 修复方案

修复时把订阅封装成显式的 disposable，并在窗口生命周期结束时统一释放。为了避免后续回归，新增了一条长时间运行的压力脚本。

> 这类问题最容易被短测试漏掉，必须让复现路径覆盖真实的停留时间。

## 复盘与总结

根因不是某个昂贵对象本身，而是生命周期边界没有被代码表达出来。后续会把跨进程订阅统一收敛到一个更窄的接口里。
